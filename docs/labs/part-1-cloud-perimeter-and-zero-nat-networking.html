1. The Zero-NAT Architecture

In traditional AWS reference architectures, standard compliance templates dictate a rigid pattern: compute instances must live in private subnets, and all internet-bound traffic must route through an AWS Managed NAT Gateway. While this provides an outbound-only barrier, it introduces a severe financial penalty that kills early-stage cloud economics.

Let's look at the cold numbers of an AWS Managed NAT Gateway:

  • Hourly Existence Fee: $0.045 / hour × 720 hours = $32.40 / month per AZ.
  • Data Processing Fee: $0.045 / GB transferred through the gateway.
  • Multi-AZ Redundancy: If you place one NAT Gateway in 3 Availability Zones as recommended by default AWS Well-Architected reviews, your fixed idle network bill is $97.20 / month before your application has served a single HTTP request!

When our EC2 host runs apt-get upgrade, downloads Node.js runtime packages, or pulls 300 MB multi-stage container images from Amazon ECR during deployments, routing that traffic through a NAT Gateway incurs a double penalty: internet data egress plus NAT data processing fees.

In the ZeetaFin Cloud Platform, we engineered a Zero-NAT Architecture. We route our host directly through an AWS Internet Gateway (which has zero hourly charge and zero data processing markup) and rely on AWS hypervisor-enforced stateful Security Groups for absolute ingress protection.

2. Decision Deep-Dive: Direct IGW Routing

Decision: Deploying in Public Subnet with Direct IGW Routing Architecture Decision

Code Location: infra/terraform/environments/prod/main.tf:L28-68

Why This Decision Was Made (Importance & Rationale)

Eliminates the $32.40/month baseline fee and $0.045/GB transfer fee of AWS Managed NAT Gateways. Direct connection to the Internet Gateway allows the host to pull container layers from ECR and download security updates at maximum AWS optical line speeds with zero middleware latency.

Inherent Limitation & Operational Trade-off

The compute instance is assigned a publicly routable IPv4 address. If an operator misconfigures a security group rule (e.g. opening port 5432 to 0.0.0.0/0), the database is exposed directly to the internet without a second layer of routing defense.

What Would Have Been Better (The Enterprise Alternative)

A multi-AZ private subnet topology paired with AWS VPC Endpoints (PrivateLink) for ECR, S3, and CloudWatch. PrivateLink routes all AWS API and registry traffic over internal AWS backbones, keeping the compute host completely unroutable from the public internet without requiring NAT Gateways.

Reliability Guardrail (Compensating Control)

Hypervisor-level AWS Security Groups drop all unsolicited SYN packets on non-whitelisted ports before they reach the Linux TCP stack. Database port 5432 is strictly bound to the internal Docker bridge network and has zero inbound ingress rules in the security group.

3. Decision Deep-Dive: Bypassing the Application Load Balancer

Decision: Direct Security Group Ingress vs. AWS ALB Perimeter Ingress

Code Location: infra/terraform/environments/prod/main.tf:L71-114

Why This Decision Was Made (Importance & Rationale)

An AWS ALB costs a fixed ~$16.20/month plus LCU usage fees (~$0.008 per LCU-hour). For a single compute node in early production, an ALB adds unnecessary cost, additional proxy hops, and complexity. Binding ports 3000 and 3001 directly to host interfaces delivers raw line-rate performance.

Inherent Limitation & Operational Trade-off

No native AWS-managed TLS edge termination (requires Let's Encrypt or an external reverse proxy). No native AWS WAF integration for edge Layer 7 SQL injection/XSS filtering. Inability to do weighted blue/green traffic shifting across multiple targets.

What Would Have Been Better (The Enterprise Alternative)

An Application Load Balancer terminating an AWS Certificate Manager (ACM) wildcard certificate, routing traffic based on host/path headers (api.zeetafin.com ➔ Backend Target Group, app.zeetafin.com ➔ Frontend Target Group), integrated with AWS WAF for automated bot and DDoS mitigation.

Reliability Guardrail (Compensating Control)

Application-level defense: NestJS enforces a global ValidationPipe with whitelist: true (automatically stripping unvalidated properties from payloads) and integrates Helmet HTTP security headers to protect against clickjacking, MIME sniffing, and cross-site scripting.

4. Decision Deep-Dive: Dynamic Public IPv4 vs Elastic IP (EIP)

Decision: Using map_public_ip_on_launch = true instead of Elastic IP IP Management

Code Location: infra/terraform/environments/prod/main.tf:L48

Why This Decision Was Made (Importance & Rationale)

As of February 1, 2024, AWS charges $0.005 per hour ($3.60/month) for every public IPv4 address, whether attached to a running instance or unattached. Auto-assigning a dynamic public IP simplifies Terraform code and avoids managing dangling Elastic IP allocations during teardown and recovery drills.

Inherent Limitation & Operational Trade-off

If the EC2 instance is stopped and started (or rebuilt via disaster recovery), AWS assigns a new public IPv4 address. DNS records (Route 53) and CI/CD secret variables (EC2_HOST) must be updated upon replacement.

What Would Have Been Better

An Elastic IP combined with an automated Amazon Route 53 A-record update via Terraform, providing an immutable public IP address for DNS records.

Reliability Guardrail

The Terraform configuration dynamically generates the Ansible inventory file (hosts.ini) at apply time using the live assigned public IP, ensuring automation playbooks never target stale IP addresses.

5. Terraform Code Anatomy

Let's inspect the exact lines of code in infra/terraform/environments/prod/main.tf that implement this zero-NAT perimeter:

infra/terraform/environments/prod/main.tf (Perimeter Rules) HCL 
# 1. Isolated Virtual Private Cloud
resource "aws_vpc" "main" {
  cidr_block           = "10.0.0.0/16" # 65,536 private IP addresses
  enable_dns_support   = true          # Enables AWS Route 53 resolver
  enable_dns_hostnames = true          # Gives EC2 public DNS hostnames

  tags = { Name = "zeetafin-prod-vpc" }
}

# 2. Free Ingress/Egress Gateway (Bypasses NAT Gateway fees)
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
  tags   = { Name = "zeetafin-prod-igw" }
}

# 3. Public Subnet with Direct IGW Routing
resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24" # 256 IPs (251 usable by workloads)
  availability_zone       = "us-east-1a"
  map_public_ip_on_launch = true          # Dynamic public IP

  tags = { Name = "zeetafin-prod-public-subnet" }
}

# 4. Default Route Table pointing 0.0.0.0/0 to the IGW
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }

  tags = { Name = "zeetafin-prod-public-rt" }
}

# 5. Associating Subnet to the Internet Route Table
resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

6. SRE Failure & Triage Forensics

Scenario 1: The Gateway Blackhole Outage

The Incident: An engineer attempts to optimize routing and creates a subnet without associating it to the route table containing the Internet Gateway route.

SRE Triage TerminalINCIDENT
$ ssh -i ~/.ssh/zeetafin-key ubuntu@54.89.21.14
ssh: connect to host 54.89.21.14 port 22: Connection timed out

# Inspecting Route Tables via AWS CLI:
$ aws ec2 describe-route-tables --filters "Name=vpc-id,Values=vpc-0a1b2c3d" --query "RouteTables[*].Routes"
[
    [
        {
            "DestinationCidrBlock": "10.0.0.0/16",
            "GatewayId": "local",
            "State": "active"
        }
        # MISSING: 0.0.0.0/0 -> igw-xxxxxx
    ]
]

Root Cause: The subnet was attached to the default "Main" route table which lacked the 0.0.0.0/0 ➔ igw-xxxx rule. Traffic had no route to the outside world, creating a network blackhole.

Remediation: Always ensure aws_route_table_association explicitly ties every public subnet to the route table pointing to aws_internet_gateway.main.id.

Scenario 2: The Port 5432 Leak Audit

The Incident: An auditor flags that PostgreSQL is running on an EC2 instance that has a public IP address.

External Port Scan (Nmap)AUDIT
$ nmap -sS -p 22,3000,3001,5432 54.89.21.14
Starting Nmap 7.94 ( https://nmap.org )
PORT     STATE    SERVICE
22/tcp   open     ssh
3000/tcp open     ppp
3001/tcp open     nessus
5432/tcp filtered postgresql  <--- PROOF: Filtered by AWS Hypervisor!

Nmap done: 1 IP address (1 host up) scanned in 2.14 seconds

Forensic Finding: Port 5432 is reported as filtered (dropped packets), proving that the AWS Security Group completely shields the database from external internet probing.
