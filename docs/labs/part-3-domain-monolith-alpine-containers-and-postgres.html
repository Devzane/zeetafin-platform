1. Monolith vs. Microservices: The Double-Entry Ledger Physics

Microservices are widely celebrated in enterprise conferences, but in core financial accounting, distributed microservices introduce catastrophic failure modes. Financial systems operate on an uncompromising mathematical law: Double-Entry Ledger Parity.

Every business event requires multiple mutations: an Accounts Payable invoice approval creates a debit in Accounts Payable and an offsetting credit in the General Ledger and Cash Management ledger. In a distributed microservice setup:

  • Each service owns its own database (Database-per-Service pattern).
  • To record an invoice across AP, GL, and Cash, you must coordinate a Distributed Saga using Apache Kafka or RabbitMQ.
  • If the network drops midway or the Cash service crashes after the AP service committed, the books are out of balance (∑ Debits ≠ ∑ Credits), requiring manual reconciliation and compensating transactions.

In ZeetaFin, we chose a Domain-Driven Modular Monolith in NestJS 10. Domain boundaries are strictly enforced via TypeScript modules and dependency injection, but all mutations execute inside a single relational database transaction (EntityManager.transaction). If any sub-operation fails, the entire transaction rolls back atomically. Zero distributed sagas, zero financial drift, zero Kafka cluster bills.

2. Decision Deep-Dive: Multi-Stage Alpine Builds

Decision: 3-Stage Multi-Stage Dockerfile (deps ➔ builder ➔ runner) Container Engineering

Code Location: apps/backend/Dockerfile & apps/frontend/Dockerfile

Why This Decision Was Made (Importance & Rationale)

A naive Node.js Docker build includes the TypeScript compiler, testing frameworks, npm caches, and OS compilers (gcc, make), generating a massive 1.2 GB to 1.4 GB image. In our 3-stage pipeline, stage 1 resolves dependencies, stage 2 compiles JavaScript and bundles Next.js standalone assets, and stage 3 copies only the pre-compiled output and production dependencies (npm ci --omit=dev). The final image size is ~158 MB (88% reduction).

Inherent Limitation & Operational Trade-off

Alpine Linux is built on musl libc rather than standard glibc. Certain native C++ Node packages (like sharp, bcrypt, or canvas) require libc6-compat or complex pre-compiled binaries.

What Would Have Been Better (The Enterprise Alternative)

Google Container Tools Distroless images (gcr.io/distroless/nodejs20-debian12), which eliminate the shell (/bin/sh) and package managers entirely, making remote code execution virtually impossible.

Cost & Network Economics

Pulling 158 MB images over AWS backbones takes 1.8 seconds versus 25 seconds for 1.2 GB images. ECR storage costs stay under $0.50/month.

3. Decision Deep-Dive: Non-Root Process Isolation

Decision: Enforcing Unprivileged Execution (UID 1000 & UID 1001) Runtime Security

Code Location: apps/backend/Dockerfile:L31 (USER node) & apps/frontend/Dockerfile:L39 (USER nextjs)

Why This Decision Was Made (Importance & Rationale)

By default, Docker containers execute as root (UID 0). If an application vulnerability allows Remote Code Execution (RCE), the attacker operates as root. If a container breakout flaw exists in the Linux kernel (such as Dirty COW or runc CVEs), the attacker gains full control over the underlying EC2 host. Running under unprivileged users (node UID 1000 and nextjs UID 1001) confines the attacker to an unprivileged namespace with zero write access to system directories.

Inherent Limitation & Operational Trade-off

The container process cannot bind to privileged system ports (ports below 1024 like 80 or 443) directly without Linux capabilities (CAP_NET_BIND_SERVICE).

What Would Have Been Better

Rootless Docker daemons paired with AppArmor and seccomp profiles enforcing strict Linux system call allowlists.

Reliability Guardrail

Zero monetary cost. Ensures compliance with CIS Docker Benchmark Level 1 recommendations.

4. Self-Hosted PostgreSQL 16 vs. AWS RDS Multi-AZ

Decision: Containerized PostgreSQL 16 on Docker Named Volume Persistence

Code Location: deploy/docker-compose.prod.yml:L2-21

Why This Decision Was Made (Importance & Rationale)

AWS charges an exorbitant markup for managed relational databases: an Amazon RDS PostgreSQL Multi-AZ instance (db.t3.medium with 20 GB storage) costs ~$118.00 / month ($1,416 / year). By self-hosting PostgreSQL 16 Alpine directly inside Docker on our encrypted gp3 EBS volume, the database costs ~$1.60/month (only disk storage), delivering full superuser administrative autonomy and zero RDS license markups.

Inherent Limitation & Operational Trade-off

No automated point-in-time recovery (PITR) with continuous WAL archiving out-of-the-box. If the compute host hardware degrades, automated failover is manual rather than instant.

What Would Have Been Better (The Enterprise Alternative)

Amazon Aurora PostgreSQL Serverless v2 with automated multi-AZ replication, 6-way storage replication across 3 AZs, and automated sub-minute Point-in-Time Recovery.

Reliability Guardrail (Compensating Control)

Database state lives in a Docker named volume (zeetafin_prod_pgdata) backed by the host's AWS EBS volume. Data survives container restarts and upgrades. Disaster recovery snapshots are automatically backed up to encrypted Amazon S3 storage.

5. Production Compose Manifest Anatomy

Inspect the service dependency graph and network quarantine implemented in deploy/docker-compose.prod.yml:

deploy/docker-compose.prod.yml YAML 
services:
  db:
    image: postgres:16-alpine
    container_name: zeetafin-db-prod
    restart: unless-stopped
    volumes:
      - zeetafin_prod_pgdata:/var/lib/postgresql/data # Persistent EBS volume
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-postgres} -d ${POSTGRES_DB:-zeetafin}"]
      interval: 10s
      timeout: 5s
      retries: 5
    networks:
      - zeetafin-prod-net

  backend:
    image: ${ECR_REGISTRY}/zeetafin-backend:${IMAGE_TAG:-latest}
    container_name: zeetafin-backend-prod
    restart: unless-stopped
    ports:
      - "3001:3001"
    depends_on:
      db:
        condition: service_healthy # Eliminates database boot race condition!
    healthcheck:
      test: ["CMD-SHELL", "wget --spider http://127.0.0.1:3001/api/docs || exit 1"]
    networks:
      - zeetafin-prod-net

  frontend:
    image: ${ECR_REGISTRY}/zeetafin-frontend:${IMAGE_TAG:-latest}
    container_name: zeetafin-frontend-prod
    restart: unless-stopped
    ports:
      - "3000:3000"
    depends_on:
      backend:
        condition: service_healthy # Next.js only starts after API is ready!
    networks:
      - zeetafin-prod-net

volumes:
  zeetafin_prod_pgdata:
    name: zeetafin_prod_pgdata # Preserved across container deletions

networks:
  zeetafin-prod-net:
    name: zeetafin-prod-net
    driver: bridge

6. SRE Incident Forensics

Scenario 1: The Database Boot Race Condition Disaster

The Incident: A developer removes condition: service_healthy from docker-compose.prod.yml and restarts the stack.

Docker Logs OutputCRASH LOOP
[Nest] 1  - 10/27/2026, 3:15:22 PM   ERROR [TypeOrmModule] Unable to connect to the database.
Error: connect ECONNREFUSED 172.18.0.2:5432
    at TCPConnectWrap.afterConnect [as oncomplete] (node:net:1605:16)
[Nest] 1  - 10/27/2026, 3:15:23 PM   ERROR [NestApplication] Failed to start API Gateway. Process exited with code 1.

Root Cause: PostgreSQL takes ~4 seconds to initialize shared memory and open its TCP socket. Without condition: service_healthy, Docker starts NestJS immediately upon PostgreSQL container creation, causing TypeORM to crash on a closed socket.

Remediation: Always enforce condition: service_healthy with pg_isready tests, ensuring dependent containers never start prematurely.
