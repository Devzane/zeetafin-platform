The Golden Rule If running your playbook a second time produces changes, your automation is brittle and will cause deployment failures in production.

1. What is Idempotency in SRE?

In computer science and site reliability engineering, an operation is idempotent if applying it multiple times yields the exact same result as applying it once:

$$\Large f(f(x)) \equiv f(x)$$

When you execute an Ansible playbook across a fleet of 50 production nodes, you must have absolute mathematical confidence that a re-run will not restart healthy containers, rewrite stable config files, or trigger system downtime unless the target configuration actually drifted.

The Zero-Drift Benchmark

First Run: ok=8, changed=6, unreachable=0, failed=0
Second Run: ok=8, changed=0, unreachable=0, failed=0

2. Running the Idempotency Test

Execute the second run immediately following Lab 03. Every task must report ok with zero changed tasks:

terminal — secondary idempotency run
BASH
# Run playbook a second time against the provisioned host
cd infra/ansible
ansible-playbook playbook.yml

# Expected PLAY RECAP:
# zeetafin_host : ok=8 changed=0 unreachable=0 failed=0 skipped=0 rescued=0 ignored=0

3. Hands-on Drift Simulation Drill

To prove that your playbook is truly self-healing, manually inject configuration drift by deleting the Docker GPG keyring on the server, then observe Ansible automatically restore it:

terminal — drift injection & self-healing test
BASH
# 1. SSH into host and manually remove the Docker GPG key
ssh -i ~/.ssh/zeetafin-key ubuntu@$(cd ../terraform && terraform output -raw ec2_public_ip)
sudo rm -f /etc/apt/keyrings/docker.gpg
exit

# 2. Run Ansible in dry-run mode (check mode)
ansible-playbook playbook.yml --check

# Notice Ansible detects missing key and flags: changed=1

# 3. Re-run live playbook to auto-heal drift
ansible-playbook playbook.yml

# 4. Confirm key has been restored
ssh -i ~/.ssh/zeetafin-key ubuntu@$(cd ../terraform && terraform output -raw ec2_public_ip) \
  "ls -la /etc/apt/keyrings/docker.gpg"

4. Linux Socket & Group Debugging

When containers fail to start or developers cannot run docker commands, the root cause is almost always Unix domain socket permissions:

terminal — inspecting unix socket permissions
BASH
# Check socket ownership and permissions
ls -la /var/run/docker.sock
# Expected output:
# srw-rw---- 1 root docker 0 Oct 28 12:00 /var/run/docker.sock

# Inspect group membership for user ubuntu
id ubuntu
# Must show: uid=1000(ubuntu) gid=1000(ubuntu) groups=1000(ubuntu),...,999(docker)

# If docker group is present but active shell lacks permissions:
newgrp docker

5. Systemd Journal Diagnostics

terminal — systemd journal troubleshooting
BASH
# 1. Check detailed status of docker service
sudo systemctl status docker.service --no-pager

# 2. View recent 50 lines of docker daemon logs
sudo journalctl -u docker.service -n 50 --no-pager

# 3. Check for iptables / bridge errors
sudo journalctl -u docker.service | grep -i "bridge"

6. Production Troubleshooting Matrix

Symptom Investigation Step Remediation
Second playbook run reports changed > 0 Check which specific task changed in Ansible stdout. Tasks using raw shell commands without creates or changed_when: false violate idempotency. Add guard clauses.
dial unix /var/run/docker.sock: connect: permission denied Run groups to check active shell groups. Run newgrp docker or log out and reconnect SSH to refresh user session tokens.
Docker daemon crashes on start Inspect journalctl -u docker.service. Check for invalid JSON in /etc/docker/daemon.json or IP collision on 172.17.0.0/16 (default bridge).
Playbook hangs on APT task Run ps aux | grep apt on the remote server. Another process or automatic unattended-upgrades holds /var/lib/dpkg/lock. Kill hanging PID or wait for release.

7. Hardening Checklist

  • [x] Secondary playbook execution confirms 100% idempotency (changed=0, failed=0).
  • [x] Check mode (--check) functions cleanly without side effects.
  • [x] Intentional configuration drift simulated and self-healed by Ansible.
  • [x] Docker socket permissions verified as srw-rw---- root docker.
  • [x] Non-root ubuntu user verified capable of communicating with socket.
  • [x] Systemd journal health logs confirmed clean with zero bridge or network errors.
