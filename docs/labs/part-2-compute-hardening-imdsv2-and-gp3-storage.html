1. Compute Density vs. Kubernetes Cluster Bloat

In modern cloud conversations, the knee-jerk answer to hosting containerized workloads is "spin up an Amazon EKS cluster". But for an enterprise startup or financial system processing thousands of transactions a day, deploying Kubernetes is often an expensive architectural mistake.

Consider the structural overhead of an Amazon EKS cluster:

  • The Control Plane Tax: AWS charges a flat $73.00 / month ($0.10/hour) just to keep the Kubernetes control plane running.
  • Daemon Memory Tax: In a Kubernetes node, system agents (the Kubelet, kube-proxy, CoreDNS, AWS VPC CNI, and logging daemons) consume 1.2 GB to 1.5 GB of RAM before your application containers start.
  • Compute Sizing Inflation: To run our 3-tier financial ERP (Next.js + NestJS + Postgres), Kubernetes requires at least two t3.medium or t3.large worker nodes to achieve high-availability quorum, driving monthly costs past $150.00 to $220.00.

By selecting a single hardened t3.medium EC2 instance (2 vCPU, 4GB RAM) running native Docker CE, 100% of the memory and CPU are dedicated to the application and database. Total compute cost: ~$25/month (or ~$14/month on an EC2 Compute Savings Plan).

2. Decision Deep-Dive: IMDSv2 Anti-SSRF Defense

Decision: Enforcing IMDSv2 with http_put_response_hop_limit = 1 Security Hardening

Code Location: infra/terraform/environments/prod/main.tf:L166-170

Why This Decision Was Made (Importance & Rationale)

Neutralizing Server-Side Request Forgery: In legacy IMDSv1, any application flaw that allowed user-controlled HTTP requests (e.g., an invoice generator scraping an external image) allowed an attacker to issue a simple GET http://169.254.169.254/latest/meta-data/iam/security-credentials/ and steal the temporary AWS IAM keys of the instance role. IMDSv2 mandates a signed PUT session token. Setting http_put_response_hop_limit = 1 guarantees that containerized workloads (which are 2 network hops away across the bridge interface) cannot exfiltrate host instance credentials because the packet's TTL expires at the bridge interface.

Inherent Limitation & Operational Trade-off

Outdated third-party monitoring agents or legacy CLI tools that do not support IMDSv2 token acquisition will fail to resolve IAM credentials.

What Would Have Been Better (The Enterprise Alternative)

Fine-grained AWS IAM Roles for Service Accounts (IRSA) or ECS Task Roles where each container has its own scoped identity, rather than an instance-wide profile.

Cost & Reliability Impact

$0.00 cost. Maximum security yield: completely eliminates the #1 attack vector for cloud account takeover.

3. Storage Physics: gp3 vs. gp2 IOPS Math

Decision: 20 GB Encrypted gp3 Root EBS Volume Disk Virtualization

Code Location: infra/terraform/environments/prod/main.tf:L172-177

Why This Decision Was Made (Importance & Rationale)

In older gp2 volumes, baseline IOPS scaled linearly with disk size at 3 IOPS per GB. A 20 GB volume only had 60 baseline IOPS, causing database write-ahead log (WAL) flushes to freeze under minimal concurrency. In gp3, AWS decoupled IOPS from volume size: every gp3 volume receives 3,000 IOPS and 125 MB/s throughput unconditionally, even at 20 GB!

Inherent Limitation & Operational Trade-off

3,000 IOPS and 125 MB/s throughput has an upper bound. Extreme high-frequency trading platforms requiring >20,000 IOPS would necessitate provisioned IOPS (io2) volumes.

What Would Have Been Better

Amazon Aurora Serverless v2 PostgreSQL with distributed storage automatically replicated 6 times across 3 Availability Zones with continuous backup to Amazon S3.

Cost Economics

gp3 costs $0.08/GB-month (20% cheaper than gp2). The 20 GB volume costs just $1.60/month while outperforming a 500 GB gp2 volume costing $50.00/month.

4. Forward-Compatible Least-Privilege IAM Roles

Decision: Zero-Permission Forward-Compatible Instance Profile IAM Security

Code Location: infra/terraform/environments/prod/main.tf:L127-154

Why This Decision Was Made (Importance & Rationale)

When provisioning an EC2 instance in Phase 1, the app makes zero AWS API calls. However, attaching an IAM instance profile after an instance is launched can require terminating and recreating the instance in older AWS workflows. We provision the IAM role and instance profile with zero policies attached. It costs nothing and allows future phases (like ECR image pulls) to attach policies with zero downtime.

Inherent Limitation & Trade-off

Any permissions attached to the host role are theoretically accessible by any process running directly on the host (outside containers).

What Would Have Been Better

OpenID Connect (OIDC) identity federation where short-lived tokens are exchanged for temporary STS credentials, eliminating static roles entirely.

Reliability Guardrail

Least-privilege principle: the role has zero permissions attached by default, guaranteeing that accidental credential exposure yields zero AWS cloud access.

5. Compute Code Anatomy

infra/terraform/environments/prod/main.tf (Compute Hardening) HCL 
# Canonical Ubuntu 24.04 LTS (Noble Numbat)
resource "aws_instance" "main" {
  ami                    = data.aws_ami.ubuntu.id
  instance_type          = "t3.medium" # 2 vCPU, 4GB RAM
  subnet_id              = aws_subnet.public.id
  vpc_security_group_ids = [aws_security_group.ec2.id]
  key_name               = aws_key_pair.main.key_name
  iam_instance_profile   = aws_iam_instance_profile.ec2.name

  # STRICT IMDSv2 ENFORCEMENT (Neutralizes SSRF)
  metadata_options {
    http_endpoint               = "enabled"
    http_tokens                 = "required"     # Blocks IMDSv1 calls with HTTP 401
    http_put_response_hop_limit = 1              # Limits packet TTL to exactly 1 hop
  }

  # HIGH-PERFORMANCE LOW-COST STORAGE (3,000 Baseline IOPS)
  root_block_device {
    volume_type           = "gp3"
    volume_size           = 20
    encrypted             = true
    delete_on_termination = true
  }

  tags = { Name = "zeetafin-prod-server" }
}

6. SRE Incident Forensics

Scenario 1: The Container SSRF Exfiltration Attempt

The Incident: An attacker exploits an SSRF flaw inside the NestJS application container and tries to pull AWS credentials.

Container Shell (UID 1000)ATTACK ATTEMPT
# 1. Attacker attempts legacy IMDSv1 GET request:
$ curl -i http://169.254.169.254/latest/meta-data/iam/security-credentials/
HTTP/1.1 401 Unauthorized
Content-Type: text/plain

# 2. Attacker attempts to acquire an IMDSv2 session token:
$ curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60"
curl: (28) Connection timed out after 3000 milliseconds

Forensic Finding: The IMDSv1 call was rejected immediately by the hypervisor with HTTP 401. The IMDSv2 call timed out because the packet traversed the Docker bridge network (hop #1), reducing its IP TTL to 0. When it reached the host interface, it was dropped! Result: Zero credential leakage.
