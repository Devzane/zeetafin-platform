1. The Frugal Enterprise Paradox

Junior cloud engineers design systems by assembling managed AWS services like building blocks: an Application Load Balancer, a Managed NAT Gateway in each AZ, an Amazon RDS Multi-AZ PostgreSQL cluster, an Amazon EKS Kubernetes control plane, and AWS Secrets Manager. Before a single customer signs up, the AWS invoice is $350 to $500 per month.

Senior SREs design with frugal precision: understanding the physics of the operating system, the Linux network stack, and storage virtualization to deliver 99.9% availability, zero-downtime updates, and sub-15-minute disaster recovery on an infrastructure footprint costing less than $25 per month.

The Core Engineering Thesis

Cost reduction is dangerous only when it introduces unquantified single points of failure. In ZeetaFin, every cost optimization decision is paired with an explicit, automated compensating reliability control (e.g., EBS persistence, automated healthcheck polling, IMDSv2 anti-SSRF enforcement, and 30-second SHA rollbacks).

2. Cloud Perimeter & Network Decisions

Decision 2.1: Single Public Subnet with Direct IGW (Bypassing AWS NAT Gateway) Networking

Code Location: infra/terraform/environments/prod/main.tf:L28-68

We deploy our compute host into a single public subnet (10.0.1.0/24) routed directly to an AWS Internet Gateway, assigning a public IP automatically (map_public_ip_on_launch = true) rather than provisioning a multi-subnet private topology with an AWS Managed NAT Gateway.

Why This Decision Was Made

An AWS NAT Gateway charges a baseline of $0.045 per hour ($32.40/month) simply to exist, plus $0.045 per GB transferred. When our EC2 host downloads Docker layers from ECR or runs Ubuntu package upgrades, NAT data fees quickly mount. A direct IGW route eliminates 100% of these idle and transfer surcharges.

Inherent Limitation & Trade-off

The EC2 compute instance has a public IP directly routable over the internet. There is no physical network DMZ separating the web application runtime from external port scanning. If a security group rule is accidentally opened to 0.0.0.0/0, the instance is immediately exposed.

What Would Have Been Better (The Enterprise Alternative)

A multi-AZ VPC across 3 Availability Zones with private subnets for compute, connected to AWS VPC Endpoints (PrivateLink) for ECR, S3, and CloudWatch. This eliminates NAT Gateways while keeping container traffic 100% inside AWS's private optical network.

Reliability Guardrail (Compensating Control)

An AWS Security Group enforced at the hypervisor layer drops all incoming packets on non-whitelisted ports. PostgreSQL port 5432 is strictly blocked from external IP ranges, ensuring only internal Docker containers can communicate with the database.

Decision 2.2: Direct Security Group Ingress vs. AWS Application Load Balancer Perimeter

Code Location: infra/terraform/environments/prod/main.tf:L71-114

Clients connect directly to the EC2 host on TCP port 3000 (Next.js) and TCP port 3001 (NestJS REST API), with packet filtering handled directly by the AWS EC2 Security Group.

Why This Decision Was Made

An AWS Application Load Balancer costs ~$16.20/month plus Load Balancer Capacity Units (LCU) charges. Direct port exposure avoids ~$25.00–$40.00/month in idle load balancing overhead while delivering maximum throughput with zero proxy hops.

Inherent Limitation & Trade-off

No managed TLS edge termination (requires Let's Encrypt or an external reverse proxy). No native AWS WAF integration for edge Layer 7 SQLi/XSS filtering. Inability to do weighted canary traffic shifting across multiple backend targets.

What Would Have Been Better (The Enterprise Alternative)

An Application Load Balancer terminating an AWS Certificate Manager (ACM) wildcard certificate, routing traffic based on host headers (api.zeetafin.com to backend, app.zeetafin.com to frontend), protected by AWS WAF rate-limiting rules.

Reliability Guardrail (Compensating Control)

The NestJS application implements a global ValidationPipe with whitelist: true (stripping unvalidated request payload parameters) and Helmet HTTP security headers, protecting application memory from buffer overflows and malicious script injection.

3. Compute, IMDSv2 & EBS Decisions

Decision 3.1: Enforcing AWS IMDSv2 with hop-limit = 1 Security Hardening

Code Location: infra/terraform/environments/prod/main.tf:L166-170

main.tf (IMDSv2 Enforcement)HCL
metadata_options {
  http_endpoint               = "enabled"
  http_tokens                 = "required"     # Rejects insecure IMDSv1 calls (HTTP 401)
  http_put_response_hop_limit = 1              # Limits packet TTL to exactly 1 network hop
}
Why This Decision Was Made

Anti-SSRF Armor: In legacy IMDSv1, an attacker who discovered an SSRF vulnerability (e.g., an invoice generator scraping a URL) could issue GET http://169.254.169.254/latest/meta-data/iam/security-credentials/ to steal the instance's AWS temporary credentials. IMDSv2 mandates a signed PUT session token. Setting http_put_response_hop_limit = 1 ensures that packets originating from inside Docker containers (which are 2 hops away across the bridge interface) expire before reaching the metadata endpoint.

Inherent Limitation & Trade-off

Legacy monitoring agents, older third-party SDKs, or outdated CLI scripts that do not implement tokenized IMDSv2 authentication will fail to resolve IAM credentials.

What Would Have Been Better (The Enterprise Alternative)

Container-scoped IAM identities using IAM Roles for Service Accounts (IRSA) or ECS Task IAM Roles, completely isolating credentials per container so the host never requires an instance profile.

Cost & Reliability Impact

$0.00 cost. Yields enterprise bank-grade defense against total AWS cloud infrastructure takeover from containerized application vulnerabilities.

Decision 3.2: 20 GB Encrypted gp3 Root EBS Storage Persistence

Code Location: infra/terraform/environments/prod/main.tf:L172-177

Why This Decision Was Made

Unlike older gp2 volumes (where IOPS were tied strictly to volume size at 3 IOPS/GB, giving a 20 GB volume an unusable 60 IOPS), gp3 provides 3,000 baseline IOPS and 125 MB/s throughput unconditionally, even on a minimal 20 GB drive. PostgreSQL write-ahead logs (WAL) and ACID journal commits never stall on disk I/O queues.

Inherent Limitation & Trade-off

3,000 IOPS and 125 MB/s throughput has an upper bound. High-frequency enterprise transactional workloads exceeding 5,000 queries per second would require provisioned IOPS.

What Would Have Been Better

Amazon Aurora Serverless v2 PostgreSQL with distributed storage automatically replicated 6 times across 3 Availability Zones with continuous backup to Amazon S3.

Cost Economics

gp3 is 20% cheaper than gp2 ($0.08/GB vs $0.10/GB). 20 GB costs just $1.60/month, saving hundreds compared to managed RDS database instances.

4. Configuration Management Decisions

Decision 4.1: Ansible with Dynamic Templated Inventory vs. Cloud-Init Configuration

Code Location: infra/ansible/site.yml and infra/ansible/roles/docker_host/

Why This Decision Was Made

Zero Configuration Drift: Raw bash scripts inside EC2 user_data execute once on first launch and fail silently without structured logging. Ansible is declarative and idempotent. Running ansible-playbook site.yml a second time produces changed=0, proving the production environment has not drifted.

Inherent Limitation & Trade-off

Bootstrapping an instance requires waiting for SSH availability and running apt package installations, taking 2–4 minutes during initial host setup.

What Would Have Been Better

HashiCorp Packer Golden AMIs: Pre-compiling Docker and security hardening into a private AMI during the CI phase. Instances launched from a Golden AMI boot in 15 seconds without running package upgrades.

Reliability Guardrail

Ansible pre-tasks explicitly poll the system until /var/lib/dpkg/lock-frontend is released, preventing aborted package installs caused by Ubuntu background unattended updates.

5. Application & Containerization Decisions

Decision 5.1: Domain-Driven Modular Monolith (NestJS 10) vs. Microservices Architecture

Code Location: apps/backend/src/ (GL, AP, AR, Cash, Budgeting, Assets)

Why This Decision Was Made

Double-Entry Ledger Integrity: Financial accounting requires strict parity: every debit must be balanced by an equal credit (∑ Debits ≡ ∑ Credits). In a distributed microservice setup, recording a journal entry across AP, GL, and Cash requires distributed sagas, 2-phase commits, and message brokers (Kafka/RabbitMQ). A modular monolith executes these operations inside a single database transaction (EntityManager.transaction), guaranteeing ACID consistency with zero network latency.

Inherent Limitation & Trade-off

The entire backend must be compiled and deployed together. A memory leak or heavy reporting query in the Fixed Assets module could theoretically impact API responsiveness for General Ledger endpoints.

What Would Have Been Better

CQRS (Command Query Responsibility Segregation) with read/write database segregation and event-driven projections using Apache Kafka or AWS EventBridge.

Cost Optimization Angle

Eliminates the cost of running multiple container services, service meshes, and managed Kafka clusters (saving $150–$300/month).

Decision 5.2: Multi-Stage Alpine Builds & Non-Root Execution Container Security

Code Location: apps/backend/Dockerfile & apps/frontend/Dockerfile

Why This Decision Was Made

Attack Surface Minimization: Compilers, npm devDependencies, and build tools are purged in stage 2. Production images contain only compiled JavaScript and runtime dependencies. NestJS API dropped from 1.2 GB to 158 MB; Next.js frontend dropped from 1.4 GB to 139 MB using output: 'standalone'. Containers run as unprivileged users (node UID 1000 and nextjs UID 1001).

Inherent Limitation & Trade-off

Alpine uses musl libc instead of standard glibc. Native C++ Node modules occasionally require compatibility libraries (libc6-compat).

What Would Have Been Better

Google Container Tools Distroless images, which contain no shell (/bin/sh) whatsoever, making interactive command execution impossible even if an attacker gains code execution.

Reliability Guardrail

Non-root user execution guarantees that even if a container process is compromised, the attacker cannot modify system libraries or break out into the host kernel.

6. Compose & Persistence Decisions

Decision 6.1: Healthcheck-Driven Dependency Graph (condition: service_healthy) Orchestration

Code Location: deploy/docker-compose.prod.yml:L40-48

docker-compose.prod.ymlYAML
backend:
  depends_on:
    db:
      condition: service_healthy   # Waits for pg_isready before launching NestJS
frontend:
  depends_on:
    backend:
      condition: service_healthy   # Waits for HTTP 200 /api/docs before launching Next.js
Why This Decision Was Made

Eliminating Race Conditions: In naive Docker Compose setups, depends_on only checks if a container has *started*, not that it is ready to receive requests. NestJS would start before PostgreSQL finished initializing its socket, causing immediate TypeORM connection crashes. Enforcing condition: service_healthy guarantees sequential, verified startup.

Inherent Limitation & Trade-off

Adds 15–25 seconds of healthcheck polling delay to total stack initialization time.

What Would Have Been Better

Kubernetes Readiness & Liveness Probes with automated service mesh circuit-breaking (Istio/Envoy).

Reliability Guardrail

Completely prevents crash-loop restart storms upon host reboots or service updates.

7. CI/CD & Image Pipeline Decisions

Decision 7.1: Docker Buildx with GitHub Actions Native Cache (type=gha) CI/CD

Code Location: .github/workflows/cd-deploy.yml:L75-77

Why This Decision Was Made

Lightning Feedback Loops: Compiling TypeScript and bundling Next.js applications from scratch on ephemeral GitHub Actions runners takes 6–8 minutes per push. Buildx with cache-from: type=gha caches intermediate Docker image layers directly inside GitHub's cache backend, cutting build times down to 35–45 seconds.

Inherent Limitation & Trade-off

GitHub Actions enforces a 10 GB cache storage limit per repository. Excessive image caching can evict older branch caches.

What Would Have Been Better

Dedicated self-hosted ephemeral build runners on AWS EC2 Spot instances equipped with NVMe SSD storage and local Docker daemon layer caches.

Cost Economics

Conserves GitHub Actions runner minutes, easily remaining within the free-tier allocation of 2,000 minutes/month.

Decision 7.2: Immutable Git SHA Tagging (${{ github.sha }}) Registry Hygiene

Code Location: .github/workflows/cd-deploy.yml:L72-74

Why This Decision Was Made

Auditability & Determinism: Using mutable tags like :latest creates ambiguity in production: if a bug occurs, you cannot easily identify which commit introduced it. Pushing an immutable Git SHA tag (e.g., sha-9f2b84c) links every running container directly to its exact source code commit.

Inherent Limitation & Trade-off

Rapid deployment pipelines accumulate hundreds of tagged images in Amazon ECR over time.

What Would Have Been Better

Automated cryptographic image signing with Cosign/Sigstore and vulnerability admission controllers verifying image signatures at runtime.

Cost & Reliability Guardrail

Terraform provisions an automated ECR Lifecycle Policy that purges untagged layers and retains only the last 30 releases, capping ECR storage costs to under $1.00/month.

8. Deployment & Rollback Decisions

Decision 8.1: In-Place Atomic Container Swapping Zero-Downtime

Code Location: deploy/scripts/deploy.sh:L94-100

Why This Decision Was Made

Zero Port Collisions: Pre-pulling images via docker compose pull ensures that download delays do not occur while containers are offline. Executing docker compose up -d --remove-orphans --force-recreate recreates the containers in milliseconds, binding ports cleanly without port conflict errors.

Inherent Limitation & Trade-off

A brief sub-second TCP reset window can occur as the host network stack hands off the listening socket to the new container process.

What Would Have Been Better

Blue/Green deployment using reverse proxies (Nginx/Traefik) where the new version is fully warmed before traffic is shifted.

Cost & Reliability Guardrail

Delivers smooth container updates on a single node without requiring double compute capacity (saving 50% compute costs vs. permanent Blue/Green clusters).

Decision 8.2: Instant Git SHA Rollback Engine (rollback.sh) SRE Operations

Code Location: deploy/scripts/rollback.sh

Why This Decision Was Made

Emergency MTTR Minimization: During a live production outage, SREs should never manually edit YAML files or debug git branches. Running ./scripts/rollback.sh sha-9f2b84c updates the environment tag, pulls the verified historical release, restarts containers, and validates health in under 30 seconds.

Inherent Limitation & Trade-off

Code rollbacks cannot automatically reverse destructive database schema migrations (e.g., dropped columns).

What Would Have Been Better

Automated database backward-compatible expand/contract migrations managed by automated Canary rollback controllers (e.g., Argo Rollouts).

Reliability Guardrail

The rollback script validates the existence of the target image in ECR before touching the active production container.

9. Disaster Recovery & S3 Decisions

Decision 9.1: Disaster Recovery Protocol: Declarative IaC + S3 Tarball Restores Business Continuity

Code Location: docs/runbooks/disaster-recovery.md

Why This Decision Was Made

RTO < 15 min, RPO < 1 hr: If the physical EC2 host is destroyed, Terraform recreates the VPC and instance in 3 minutes, Ansible configures Docker in 2 minutes, the PostgreSQL snapshot is extracted from encrypted S3 in 4 minutes, and containers start in 2 minutes. Total recovery is achieved in under 15 minutes.

Inherent Limitation & Trade-off

RPO is tied to snapshot cadence (hourly backups = up to 1 hour of transaction loss).

What Would Have Been Better

Continuous Write-Ahead Log (WAL) streaming to S3 using pgBackRest or WAL-G for sub-minute Point-in-Time Recovery (PITR).

Cost Economics

S3 standard storage for compressed database backups costs ~$0.05/month, avoiding high RDS cross-region replication fees.

10. Real-World SRE Disaster Scenarios

Scenario A: The Malicious SSRF Attack Attempt

An attacker discovers an SSRF flaw in an invoice export feature and attempts to read AWS IAM credentials from the metadata IP address.

Attacker Exploit Attempt Inside ContainerSIMULATION
$ curl -i http://169.254.169.254/latest/meta-data/iam/security-credentials/
HTTP/1.1 401 Unauthorized
Content-Type: text/plain

# The attacker attempts an IMDSv2 token request:
$ curl -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 60"
curl: (28) Connection timed out after 3000 milliseconds

Forensic Analysis: The legacy IMDSv1 call was rejected with HTTP 401 because http_tokens = "required" was enforced in Terraform. The IMDSv2 token request failed because http_put_response_hop_limit = 1 dropped the packet at the Docker bridge boundary. Result: Account credentials remained safe.
