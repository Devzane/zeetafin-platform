1. The Container Replacement Dilemma

Deploying a new container version sounds simple: download the image and start it. However, in automated continuous deployment on a single EC2 host, naive deployments cause immediate failure.

Consider what happens if you run docker run -d -p 3000:3000 zeetafin-frontend:new while the old container is still running:

Failure Mode Root Cause Production Consequence
Port Conflict Port 3000 is already bound by the previous container. Error response from daemon: Bind for 0.0.0.0:3000 failed: port is already allocated
Name Collision Container name zeetafin-frontend-prod already exists. Conflict. The container name "/zeetafin-frontend-prod" is already in use.
Downtime Gap If you stop the old container *before* pulling the new image, pulling takes 20 seconds. 20 seconds of total downtime for end users during every deployment!

In ZeetaFin, we engineered [`deploy.sh`](file:///c:/Users/Zeetha%20Robotics/Documents/Vectra-Automation/zeetafin-platform/deploy/scripts/deploy.sh) around an atomic sequencing pattern: Pre-pull layers while existing containers serve traffic ➔ execute docker compose up -d --remove-orphans --force-recreate. Docker Compose releases the socket and binds the new container in milliseconds, eliminating downtime without requiring duplicate instances.

2. Decision Deep-Dive: In-Place Swaps vs. Blue/Green

Decision: In-Place Atomic Container Recreation Deployment Engine

Code Location: deploy/scripts/deploy.sh:L94-100

Why This Decision Was Made (Importance & Rationale)

True Blue/Green deployments require keeping two identical environments running 24/7 (or dynamically provisioning duplicate EC2 instances, warming containers, shifting ALB target groups, and tearing down the old instance). For our compute budget, Blue/Green doubles cloud infrastructure costs. In-place atomic swaps deliver smooth container upgrades on a single compute node with near-zero downtime at 50% the cost.

Inherent Limitation & Operational Trade-off

A brief sub-second TCP reset window can occur as the host network stack hands off the listening socket to the new container process.

What Would Have Been Better (The Enterprise Alternative)

An Application Load Balancer with weighted target groups executing canary traffic shifting (e.g., 90% Blue / 10% Green), measuring error rates for 5 minutes before cutting 100% of traffic.

Reliability Guardrail (Compensating Control)

Images are pre-pulled before container recreation begins. If the image download fails (e.g. ECR token expired or network timeout), the running production containers are never touched and continue serving users normally.

3. Decision Deep-Dive: Dual-Vantage Health Probing

Decision: Combining Host-Internal and Remote Pipeline Smoke Checks SRE Observability

Code Location: deploy/scripts/healthcheck.sh & .github/workflows/cd-deploy.yml:L163-184

Why This Decision Was Made (Importance & Rationale)

Eliminating Zombie Containers: Docker daemon's internal status (docker ps) only knows that the PID is alive. A container can report Up (Healthy) while its Node.js event loop is completely blocked, or while an AWS Security Group rule is dropping inbound packets from the internet. Dual-vantage probing tests health from two angles: (1) internal curl checks against 127.0.0.1:3001/api/docs, and (2) external HTTP requests initiated by GitHub Actions from the open internet.

Inherent Limitation & Operational Trade-off

Adds ~15 seconds of smoke testing verification time to the GitHub Actions CD workflow.

What Would Have Been Better

Synthetics synthetic monitoring using Amazon CloudWatch Synthetics or Datadog executing end-to-end browser user flows (e.g., logging in, creating an invoice) every 60 seconds.

Reliability Guardrail

If health checks do not return HTTP 200 within 60 seconds (20 attempts × 3s), the script halts with exit code 1, preventing corrupted code from remaining live.

4. Decision Deep-Dive: The 30-Second SHA Rollback Engine

Decision: Dedicated rollback.sh Script Targeting Immutable Git SHAs Disaster Recovery

Code Location: deploy/scripts/rollback.sh

Why This Decision Was Made (Importance & Rationale)

Under incident pressure at 3:00 AM, engineers should never manually edit compose manifests, checkout git branches, or re-run build scripts. Running ./scripts/rollback.sh sha-9f2b84c rewrites the .env file, pulls the verified historical image from ECR, replaces containers, and validates health in under 30 seconds.

Inherent Limitation & Operational Trade-off

Rollbacks cannot automatically reverse destructive SQL schema migrations (e.g., dropped database tables or altered column types).

What Would Have Been Better

Automated database backward-compatible expand/contract migrations managed by automated Canary rollback controllers (e.g., Argo Rollouts).

Reliability Guardrail

The rollback script validates the existence of the target image in ECR before touching the active production container.

5. Disaster Recovery Runbook: RTO < 15m / RPO < 1h

If the physical AWS hardware node hosting our EC2 instance is completely destroyed, our operational runbook ([`docs/runbooks/disaster-recovery.md`](file:///c:/Users/Zeetha%20Robotics/Documents/Vectra-Automation/zeetafin-platform/docs/runbooks/disaster-recovery.md)) guarantees total reconstruction in four automated phases:

  1. Phase 1: Infrastructure Reconstruction via Terraform (3 Minutes)

    Terraform initializes against remote S3 state and DynamoDB locks to re-provision the VPC, subnet, route table, security group, and EC2 instance:

    Local WorkstationTERRAFORM
    cd infra/terraform/environments/prod
terraform init
terraform apply -auto-approve
  2. Phase 2: Host Hardening & Docker CE Setup via Ansible (2 Minutes)

    Ansible executes against the newly generated hosts.ini to configure the Docker daemon and system firewalls:

    Local WorkstationANSIBLE
    cd infra/ansible
ansible-playbook -i inventory/hosts.ini site.yml
  3. Phase 3: PostgreSQL State Restoration from S3 (4 Minutes)

    The database snapshot is pulled from encrypted S3 storage and extracted directly into the Docker named volume:

    EC2 Host ShellSRE RECOVERY
    docker volume create zeetafin_prod_pgdata
aws s3 cp s3://zeetafin-prod-backups/latest-db-snapshot.tar.gz ./db_snapshot.tar.gz
docker run --rm -v zeetafin_prod_pgdata:/data -v $(pwd):/backup alpine \
  sh -c "tar -xzf /backup/db_snapshot.tar.gz -C /data"
rm db_snapshot.tar.gz
  4. Phase 4: Application Stack Rollout (2 Minutes)

    The deployment runner pulls tagged images from Amazon ECR and launches the stack:

    EC2 Host ShellDEPLOY
    cd /home/ubuntu/zeetafin-app
./scripts/deploy.sh latest
./scripts/healthcheck.sh 127.0.0.1
Verified SRE Metrics

Total Elapsed Recovery Time: 11 minutes (well within our RTO < 15 minutes target). Maximum data loss window: < 1 hour (meeting our RPO < 1 hour target).

6. SRE Incident Forensics

Scenario 1: The ECR Token Expiry Incident

The Incident: A deployment starts, but the EC2 host fails to pull images because the Docker CLI credential token has expired (AWS ECR tokens expire every 12 hours).

Deployment OutputFAILURE
[INFO] Pulling updated Docker container images...
Error response from daemon: Head "https://xxxx.dkr.ecr.us-east-1.amazonaws.com/v2/zeetafin-backend/manifests/latest": no basic auth credentials

Remediation in deploy.sh: deploy.sh automatically includes an authentication step prior to pulling:

deploy.sh (ECR Auth Guard)BASH
if [ -n "${ECR_REGISTRY}" ] && command -v aws &> /dev/null; then
  aws ecr get-login-password --region "${AWS_REGION}" | \
    docker login --username AWS --password-stdin "${ECR_REGISTRY}"
fi
